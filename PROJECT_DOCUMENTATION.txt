1. PROJECT OVERVIEW
================================================================================

Purpose
  A web application that helps biomedical researchers find, filter, rank and
  understand scientific papers. PubMed is the only literature source.

Problem statement
  PubMed returns large, unranked result sets, and reading many abstracts takes
  time. Researchers need:
    - focused search with filters,
    - duplicate removal and relevance ranking,
    - reliable explanations of individual papers at a reading level they choose,
      with no invented facts, and
    - to keep up with a topic over time without repeating searches by hand.

Target users
  Biomedical researchers and students, from high-school level to PhD level (the
  three reading levels the app supports).

Long-term vision (the owner's stated goal)
  A personalized healthcare research agent that:
    (a) finds relevant PubMed papers,
    (b) synthesizes their findings across papers, and
    (c) delivers useful periodic research reports.

Status of that vision on the snapshot date

3.2 Component responsibilities (backend)
  main.py
    Installs log redaction first, then builds the FastAPI app. lifespan()
    creates one shared httpx.AsyncClient with one PubMedClient (so its rate
    limiter covers all requests), one GeminiReportGenerator, and the database
    engine and sessionmaker. It adds CORSMiddleware (exposes Retry-After), sets
    the in-memory limiters on app.state and registers the routers.
  PubMedClient
    Only talks to NCBI. Applies the rate limit and retries, and maps failures to
    PubMedTimeoutError / PubMedRateLimitError / PubMedResponseError.
  search_service.search_papers
    The search pipeline (see Section 4).
  GeminiReportGenerator
    Only talks to Gemini. Maps SDK and network errors to AnalysisError subclasses
    whose messages are safe to show users.
  analysis.analyze_paper
    Fetches the paper from PubMed, builds the prompt, calls the generator,
    validates the output and adds grounding warnings.
  usage.AiUsageGuard [BRANCH]
    Burst check, atomic reservation of the per-user and overall daily allowance
    (before Gemini is called), refund on failure, and usage snapshots.
  logging_setup.install_log_redaction [BRANCH]
    Holds HTTP-client loggers at WARNING and redacts every log record.
  routers/errors.py
    The single mapping from service errors to HTTP status codes and safe
    messages.

3.3 Component responsibilities (frontend)
  ResearchSearch.tsx
    Owns the query, filters, summary level and request lifecycle (with
    AbortController). Applies the account's preferred level, opens /?saved=<id>,
    and renders the results.
  lib/api/client.ts
    requestJson() adds credentials:"include" to every request and the
    X-Requested-With: fetch header to non-GET requests. Turns errors into
    ApiError, with user-readable messages and hints.
  AuthProvider.tsx
    Global auth state (loading / anonymous / authenticated / unavailable) and the
    log-in dialog.
  AiUsageProvider.tsx [BRANCH]
    Fetches today's AI allowance once per user (not once per card); refreshed
    after each analysis attempt. Display only: the server enforces the limit.
  SubscriptionsProvider.tsx [BRANCH]
    Loads the user's subscriptions from the server and re-fetches the list after
    every save or delete (the server is the source of truth). Hosts the
    subscription dialog and the confirmation toast.

3.4 Request flow: search
  1. Browser (http://localhost:3000): ResearchSearch.runSearch()
       -> client.searchPapers()
       -> GET http://localhost:8010/api/search?q=...&period=...&article_type=...
  2. routers/search.py
       validates input, combines the period with any custom date range
       -> search_service.search_papers()
       -> PubMedClient.esearch()  (term built by filters.build_pubmed_term;
                                   datetype=pdat when dates are set)
       -> PubMedClient.efetch()   (XML -> Paper models)
       -> deduplicate_papers -> paper_matches_date_range -> rank_papers -> trim
       -> SearchResponse JSON
  3. The browser renders the summary, the filter chips and the paper cards.
  No login and no usage limit (by decision; see Section 11).

3.5 Request flow: paper analysis
  1. User clicks "Analyze paper" (logged out on branch: "Log in to analyze"
     opens the login dialog instead)
       -> client.analyzePaper(pmid, level)
       -> POST /api/papers/{pmid}/analyze  {"summary_level": "..."}
  2. routers/analysis.py
       [BRANCH] require_user (401 if not logged in)
       [BRANCH] AiUsageGuard.reserve(): burst check, then one transaction:
                overall daily cap, then per-user daily cap (429 if reached)
       -> analysis.analyze_paper()
       -> PubMedClient.efetch([pmid])   (paper content comes from PubMed, never
                                         from the browser)
       -> build_prompt()  (system rules + level guidance + paper JSON inside
                           <paper_record> tags, with "<" escaped)
       -> GeminiReportGenerator.generate() -> parse_report() (strict validation)
       -> grounding_warnings()
       -> PaperAnalysis JSON
       [BRANCH] on ANY failure: AiUsageGuard.refund(), then a safe error.
  3. The browser renders the report and refreshes the allowance.

3.6 Request flow: accounts, preferences, saved searches, subscriptions
  The browser sends the HttpOnly session cookie (hria_session) automatically.
  The backend looks up SHA-256(token) in user_sessions; it must not be expired.
  Changes (POST/PUT/DELETE) also require the X-Requested-With: fetch header.
  Every query is filtered by the current user's id.

4. FEATURES IMPLEMENTED
================================================================================

4.1 PubMed integration  [IMPLEMENTED]
  - ESearch (JSON, sort=relevance) and EFetch (XML, rettype=abstract).
  - Every request sends db=pubmed, tool, email (if set) and api_key (if set).
  - Rate limiter: 10 requests/second with NCBI_API_KEY, 3/second without.
    NCBI_REQUESTS_PER_SECOND overrides this.
  - Retries (NCBI_MAX_RETRIES, default 2) on timeouts, HTTP 429 and 5xx, with
    exponential backoff. A Retry-After header is respected, capped at 10 s.
  - Malformed responses become a clear error: non-JSON ESearch, an
    {"error": ...} body, an ESearch ERROR field, a bad count or idlist,
    unparseable XML, or an unexpected root element.
  - A single malformed article is skipped instead of failing the whole search.
  - Parsed fields:
      title (falls back to VernacularTitle, then "[No title available]");
      structured abstract with section labels; authors (including collective
      names) and affiliation; journal;
      publication_date (PubMed's text) and publication_date_iso (YYYY,
      YYYY-MM or YYYY-MM-DD); electronic_date_iso; publication_types;
      languages; doi, doi_url, pubmed_url.
  - Unknown PMIDs are removed; repeated ids are de-duplicated.
  - [BRANCH] Connection-error messages include only the exception type, never
    the httpx message (which could contain the request URL and its api_key).

4.2 Search pipeline  [IMPLEMENTED]
  1. Candidate pool = max_results x SEARCH_CANDIDATE_MULTIPLIER (default 3),
     capped at SEARCH_MAX_CANDIDATES (default 200).
  2. Deduplication (dedup.py), in order: PMID, then DOI (case-insensitive, any
     doi.org/ or "doi:" prefix removed), then normalized title (titles of 20+
     characters only). A record with an abstract replaces a duplicate without one.
  3. Date filter (dates.py): partial dates cover their whole period ("2020" =
     2020-01-01..2020-12-31). A paper passes if its print date OR its
     electronic date overlaps the range. Undated papers are excluded unless
     include_undated=true.
  4. Ranking (ranking.py):
       score = (3 x title_overlap + 1 x abstract_overlap) / 4, range 0-1.
     Each overlap is the share of distinct query terms found in that field.
     Query terms are lowercased, accent-stripped and lightly stemmed; stopwords
     and PubMed field tags are removed. Ties keep PubMed's order. Filter tags
     never count toward the score.
  5. Trim to max_results. Warnings report skipped records, excluded undated
     papers and missing abstracts.

4.3 Filters  [IMPLEMENTED]
  - Result limit: 1-100, default 20 (SEARCH_MIN_RESULTS / SEARCH_MAX_RESULTS /
    SEARCH_DEFAULT_RESULTS).
  - Custom date range: start_date / end_date as YYYY, YYYY-MM or YYYY-MM-DD.
  - Period: all | week | month. Calculated from today's date on every request:
      week  = the 7 days before today, plus today
      month = from the same day last month (clamped, e.g. Mar 31 -> Feb 28/29)
    It is intersected with any custom range; if they don't overlap, the answer
    is 422. Filtering uses PubMed's Publication Date: datetype=pdat, which is
    the same field as [dp].
  - Article type (repeatable), sent to PubMed as [pt] terms:
      review, systematic_review, meta_analysis, randomized_controlled_trial,
      clinical_trial, observational_study, case_reports, comparative_study,
      guideline, practice_guideline
  - Language (repeatable), sent to PubMed as [la] terms:
      english, spanish, french, german, chinese, japanese, italian,
      portuguese, russian
  - Only allowlisted values are accepted; anything else is 422.
  - Several values of one filter are combined with OR; different filters with
    AND; the user's query is wrapped in parentheses.

4.4 Reading (summary) level  [IMPLEMENTED]
  - High School / College / PhD selector in the UI. Values: high_school,
    college, phd.
  - Kept across searches and sent with each analysis request.
  - Each level has its own instructions in analysis.LEVEL_GUIDANCE.
  - A signed-in user's preferred level is applied on login and whenever that
    preference changes.

4.5 Gemini paper analysis  [IMPLEMENTED; live-verified]
  - On demand only. Search never calls Gemini (test:
    test_search_never_calls_gemini).
  - Report sections (GeneratedReport):
      plain_language_overview
      research_question
      background
      methods
      key_findings
      interpretation
      limitations
      not_established
      further_questions
    Each point-list section has 1-8 points; further_questions has 1-6.
  - Every point has basis = reported | interpretation | not_reported.
  - Server-written fields (not produced by the AI):
      pmid, pubmed_url, title, summary_level, model, generated_at (UTC),
      abstract_available, source_note (says the full text was not reviewed),
      disclaimer (not medical advice), grounding_warnings.
  - Safeguards:
      - System instructions forbid invented numbers, methods or citations, and
        medical advice.
      - The paper data is marked as untrusted; "<" is escaped so the data can't
        close the <paper_record> tags.
      - Temperature 0.2.
      - No SDK retries (they would only use up quota).
      - Timeout: GEMINI_TIMEOUT_SECONDS (default 60), plus a 5 s safety margin.
      - Strict validation: JSON + Pydantic, non-empty sections, and length caps
        of 3000 (overview), 2000 (point) and 600 (question) characters.
        Fenced ```json output is accepted. Invalid output is a 502; fabricated
        content is never returned in its place.
      - Grounding check: numbers of 2+ digits and links that don't appear in
        the PubMed record are flagged in grounding_warnings.
  - Papers without an abstract: the prompt says so, abstract_available=false,
    and the source note explains the analysis is limited to metadata.
  - [BRANCH] Login required, and subject to the daily limits in Section 4.10.

4.8 Accounts, preferences, saved searches  [IMPLEMENTED]
  - Register, login, logout, current-account endpoints.
  - Passwords: Argon2id (argon2-cffi defaults), 10-128 characters, rehashed if
    the hashing parameters change.
  - Sessions:
      - Token: secrets.token_urlsafe(32), sent in an HttpOnly cookie
        hria_session (SameSite=Lax; Secure is configurable).
      - Only the SHA-256 hash of the token is stored in the database.
      - 14-day lifetime (SESSION_TTL_DAYS).
      - Logout deletes the session on the server.
  - CSRF: a required X-Requested-With: fetch header on POST/PUT/DELETE account
    routes, plus SameSite=Lax and the CORS allowlist.
  - Login throttle: 5 failures per email per 900 s, then 429 with Retry-After.
    In memory. Unknown emails are checked against a dummy hash so timing is the
    same. ([BRANCH] per-IP limits added, see 4.10.)
  - Preferences: summary_level plus up to 20 research_interests (2-100 chars
    each, de-duplicated ignoring case).
  - Saved searches: name (up to 120 chars; defaults to the query), query (2-500
    chars), filters (validated SavedSearchFilters); up to 100 per user (409
    beyond that); newest first.
  - Owner isolation: another user's saved search answers 404. Deleting a user
    cascades to all of their rows.
  - Database outages and schema problems give 503, while search keeps working.
  - Frontend: Log in / sign-up dialog, account menu, /account page (preferences
    form and saved-search list with Run / Delete), "Save search" above results,
    interest chips as one-click searches, saved searches open via /?saved=<id>.

4.9 Research subscriptions (Step A: stored settings)  [BRANCH]
  What it is: a saved "keep me updated on this topic" setting per user.
  Nothing runs on the subscription's schedule: there is no scheduler, so no
  automatic fetching, analysis or email (Step D). A user can build a digest
  from their subscriptions on demand and send a one-off test email to
  themselves (Step C, Section 4.12).
  - UI:
      - Netflix-style bell beside the Search button: outline when not
        subscribed, filled with sound waves when subscribed, swings on hover
        and after saving (skipped under reduced motion).
      - "Follow topic" on every paper card (topic prefilled with the title).
      - Dialog: topic (prefilled from the search box), Daily / Weekly / Monthly,
        delivery day (weekday for weekly, 1-28 for monthly), delivery time
        (30-minute steps), time zone (all browser IANA zones), 5 / 10 / 15 / 20
        papers, reading level (High School / General Reader, College /
        Undergraduate, Researcher / Technical), "Automatic email delivery"
        (default ON), "Email me even when there are no new papers."
      - Clear status text: settings are saved to the account, but nothing is
        sent on the schedule yet (automatic delivery needs a scheduler); a
        one-off test email can be sent from the account page.
      - Duplicates: a topic you already follow opens "Manage" instead; typing a
        duplicate offers "Manage that subscription"; the server's 409 is shown
        even for duplicates the page didn't know about.
      - /account: "Research subscriptions" list with Manage, New subscription,
        loading, error (Try again) and empty states, and an "Email delivery not
        active yet" badge.
  - Storage: research_subscriptions table (migration b4f1c80f6ca2), linked to
    the user with ON DELETE CASCADE.
  - Server-side validation: topic 2-200 chars containing letters or digits;
    frequency enum; weekday 0-6 required for weekly, month_day 1-28 required for
    monthly, the unused one cleared; delivery_time "HH:MM"; time_zone must exist
    in Python's zoneinfo database; paper_count in {5,10,15,20}; reading level
    enum; unknown fields rejected.
  - Uniqueness: UNIQUE (user_id, topic_key), where topic_key is
    services/text.normalize_title(topic) computed by the server (lowercase,
    accents removed, punctuation and spacing collapsed). The frontend's
    lib/subscriptions.topicKey applies the same rule; verified identical on
    sample inputs.
  - Database check constraints enforce frequency, schedule consistency
    (including IS NOT NULL for the required day), paper count, reading level
    and non-empty topic_key.
  - Limit: 50 subscriptions per user (409 beyond that).
  - Every response includes delivery_active=false.

4.10 Security hardening (Step B)  [BRANCH]
  - AI analysis requires login (401 otherwise; Gemini is never called).
  - Daily AI limits, enforced atomically in PostgreSQL (migration bd806695a174):
      - per user: AI_DAILY_LIMIT_PER_USER (default 20) per UTC day;
      - overall: AI_DAILY_LIMIT_TOTAL (default 200) per UTC day; 0 disables it.
    Reservation is one transaction of
      INSERT ... ON CONFLICT DO UPDATE SET used = used + 1 WHERE used < :limit
      RETURNING used
    (no row returned = limit reached -> 429 with Retry-After = seconds until
    midnight UTC). PostgreSQL row locking prevents concurrent over-use (tested
    with 12 simultaneous reservations against a limit of 5).
  - Refunds: any failure after reservation (Gemini error, timeout, invalid
    output, paper not found, PubMed outage, unexpected exception) gives the unit
    back. Only successful analyses count. Refunds never go below zero.
  - Burst brake: AI_BURST_PER_MINUTE (default 5) per user, in memory.
  - GET /api/me/ai-usage reports used / limit / remaining (also respects the
    overall cap) / resets_at.
  - Login and registration rate limits (in memory, see Section 11):
      - failed logins: 5 per email AND LOGIN_IP_MAX_FAILURES (default 20) per
        IP per LOGIN_IP_WINDOW_SECONDS (900);
      - sign-ups: REGISTER_IP_MAX_ATTEMPTS (default 5) per IP per
        REGISTER_IP_WINDOW_SECONDS (3600), counting duplicate-email attempts;
      - successful logins are never limited and do NOT reset the IP counter;
      - X-Forwarded-For is ignored unless TRUST_PROXY_HEADERS=true.
  - Secrets out of logs (app/logging_setup.py):
      - httpx, httpcore, google_genai, google.genai and urllib3 loggers held at
        WARNING (NCBI requires api_key in the URL, which httpx logs at INFO);
      - every log record (message and traceback) is redacted: values of
        api_key= / api-key= / key= / access_token= / token= / password= /
        passwd= / secret= (case-insensitive), passwords in URLs
        (scheme://user:PASSWORD@host), and the literal values of
        NCBI_API_KEY, GEMINI_API_KEY and the DATABASE_URL password (literal
        values shorter than 6 characters are not matched).
  - CORS exposes Retry-After, so browser code is allowed to read the header.
    (The current frontend doesn't read it; see "Frontend handling" below.)
  - Frontend handling (PaperAnalysisPanel.tsx, AiUsageProvider.tsx):
      - logged out: the hint reads "AI paper analysis is available to
        signed-in users"; the button "Log in to analyze" opens the login
        dialog with a reason and sends no request;
      - logged in: "N of 20 left today", from GET /api/me/ai-usage;
      - at the limit (remaining = 0): the button is disabled and the hint
        shows the reset time in the browser's local time;
      - after every attempt (success or failure) the allowance is re-fetched,
        so refunds show up immediately;
      - a server 429 (e.g. the burst limit, or the overall cap reached by
        other users) is shown as the server's own message in the error alert.
    These are display only; the server enforces every limit.
  - Search stays public with no rate limit (owner's decision for this step).

4.12 Test email digests (Step C: manual sends only)  [BRANCH]
  Automatic daily/weekly/monthly delivery is Step D and is NOT implemented.
  Live delivery VERIFIED on 2026-10-25 (about 03:40 UTC): the owner sent a
  manual test digest ("breast cancer" subscription) from /account to their own
  allowlisted address with Resend's test sender (onboarding@resend.dev), and
  confirmed it arrived. The server recorded 2 AI units that day (preview +
  send). This verifies the manual path only, to the Resend account owner's
  address; sending to other addresses (needs a verified domain) and any
  scheduled sending are NOT verified or implemented. Automated tests mock
  Resend.
  - Provider: Resend, called directly with httpx (POST /emails, Bearer key,
    Idempotency-Key header). services/email.py defines an EmailSender protocol,
    so tests use a fake and the provider can be swapped.
  - Digest content (services/digest.py), per chosen subscription (1-3):
      - the existing PubMed search for the topic, paper_count results, in a
        window from the frequency: daily and weekly = past week (PubMed can
        take days to index), monthly = past month. If the window is empty,
        the most relevant papers from any date are used, and the digest says so;
      - each paper: title (PubMed link), first 3 authors (+ "et al."),
        journal, publication date, PMID, DOI link;
      - AI summaries: ONE Gemini request per subscription summarizes all of
        its papers (2-3 sentences each) at the subscription's reading level,
        with the same evidence rules as paper analysis (records are untrusted
        data, "<" escaped). It uses 1 unit of the daily AI allowance; any
        failure refunds it. Each summary must be for a PMID that was sent, at
        most 1200 characters, and contain no numbers or links missing from
        that paper's record; otherwise it is withheld with a note;
      - if Gemini fails or the allowance is used up, the digest is still
        built, with the start of each abstract (about 320 characters) instead;
        papers without an abstract need no AI.
    There is no "new since the last digest" tracking (no history is stored).
  - Email (services/digest_render.py): inline-styled HTML plus a plain-text
    version. Everything from PubMed/Gemini is HTML-escaped and only https://
    links are rendered. Includes a "manual test, automatic delivery not active"
    notice, a source note and the not-medical-advice disclaimer.
  - Safety for test sends (routers/digests.py), all checked BEFORE any AI is
    used or email sent:
      1. EMAIL_ENABLED=true (default false) and RESEND_API_KEY set (503 otherwise);
      2. the recipient is ALWAYS the signed-in account's email; the request
         body rejects unknown fields such as "to" (422);
      3. that address must be in EMAIL_TEST_RECIPIENTS (403 otherwise), because
         accounts aren't email-verified;
      4. subscriptions must belong to the user (404 otherwise);
      5. EMAIL_TEST_SENDS_PER_HOUR per user (default 5, in memory; 429 with
         Retry-After).
    Provider-side: Resend's test sender onboarding@resend.dev only delivers
    to the Resend account owner's address.
  - Errors: Resend 401 -> 503 (key rejected); 403 -> 502 with an explanation
    of the test-sender rule; 400/422 -> 502 (check EMAIL_FROM); 429 -> 429;
    5xx or network -> 502; timeout -> 504. Only the HTTP status and Resend's
    fixed error name are logged; never the key, the recipient or Resend's
    message text. The Resend key and any "Bearer <token>" are redacted from logs.
  - Frontend (/account, TestDigestPanel.tsx): a readiness checklist (switch on,
    key set, address allowed, with the fix for each), choose 1-3
    subscriptions, "Preview digest" (sends nothing) and "Send test email",
    progress text, the Resend message ID after sending, and the digest shown
    in the page. The AI allowance is refreshed after each attempt.
  - No database changes.

4.13 Scheduled digest delivery (Step D)  [UNCOMMITTED]
  Operations, configuration, recovery and troubleshooting: docs/SCHEDULED_DIGESTS.md.
  - Safety defaults: DIGEST_DELIVERY_MODE=off and DIGEST_SCHEDULER_ENABLED=false.
    Modes: off / dry_run (built, never sent) / allowlist (EMAIL_TEST_RECIPIENTS
    only; silently "off" unless EMAIL_ENABLED, RESEND_API_KEY and the allowlist
    are all set). No unrestricted mode exists. tests/conftest.py forces both
    switches off for every test run, whatever backend/.env says.
  - Scheduling (services/schedule.py): next_run_at in UTC from the wall-clock
    schedule in the subscription's time zone; spring-forward gaps shift
    forward, fall-back repeats run once (first occurrence). Recomputed on any
    schedule/status change; NULL while email is off or unsubscribed.
  - Engine (services/delivery.py), one tick: fill missing next_run_at ->
    recover expired leases -> schedule due runs (UNIQUE subscription_id +
    scheduled_for; > grace late = skipped_missed: 6 h daily, 24 h weekly or
    monthly) -> claim with FOR UPDATE SKIP LOCKED + lease (600 s) -> recheck
    preferences/allowlist/recipient -> search PubMed (window ends on the
    scheduled local date and starts 7/14/45 days before the last SENT window's
    end, capped at 14/35/92 days; already-sent PMIDs excluded) -> one Gemini
    request from the overall daily cap only (DIGEST_MAX_AI_CALLS_PER_TICK=5) ->
    freeze subject/HTML/text/headers -> recheck under a row lock -> send with
    Idempotency-Key "digest-<id>".
  - Outcomes: sent (PMIDs, last_sent_at and the window recorded in the same
    transaction) / retry (5 min, 30 min, 2 h; DIGEST_MAX_ATTEMPTS=4) / failed
    (definitely not delivered) / needs_review (may have been delivered: never
    resent automatically). outcome_uncertain is committed before every send;
    uncertain sends are retried with the identical payload and key only within
    DIGEST_SAFE_RETRY_HOURS=23 of the first attempt (Resend keeps keys 24 h;
    it answers 409 if a key is reused with a different payload).
  - Cancellation: changing the schedule, turning email off or unsubscribing
    cancels queued deliveries (needs_review if an earlier attempt may have gone
    out).
  - Staleness (stage 4 audit fix): no digest is ever sent more than its grace
    period (6 h daily, 24 h weekly/monthly; the same MISSED_GRACE that skips
    missed runs) after its scheduled time. Every tick, in every mode including
    off, first expires queued deliveries past it: skipped_missed "expired"
    (papers stay eligible) or needs_review if possibly sent; tokens scrubbed.
  - Claim ownership (stage 4 audit fix): before freezing and before sending, a
    worker re-checks under a row lock that it still holds its lease; otherwise
    it stops ("lease_lost") and the next tick recovers the delivery.
  - Unsubscribe (services/unsubscribe.py, routers/unsubscribe.py): one random
    256-bit token per real email, SHA-256 stored on the delivery; body link to
    /unsubscribe (confirm page; opening it changes nothing) and
    List-Unsubscribe header; List-Unsubscribe-Post only when PUBLIC_API_URL is
    https. One-click POST: no cookies/CSRF, empty 200, no redirect. Idempotent.
    Invalid tokens: one generic 404; > 30 per IP per 10 min -> 429.
  - Token exposure: the plain token exists only in the email, at Resend, and in
    the stored payload while the delivery is pending/sending; every final
    status (all paths, including bulk cancellation) replaces it with
    token=removed. Access-log request lines show token=[REDACTED].
  - Operations: CLI `python -m app.jobs.digests status | run-once [--dry-run] |
    review | resolve` (review/resolve never send); GET /health reports the
    scheduler heartbeat; ticks with failed/needs_review/recovered deliveries and
    tick errors are logged as WARNING/ERROR. Test runs force the scheduler,
    scheduled sending and real email off (tests/conftest.py, verified by
    tests/test_test_safety.py).
  - Frontend: subscription status (unsubscribed / email off / next run in its
    time zone / last sent), real delivery_active badge, "Scheduled digest
    history" card, /unsubscribe page, scheduled-mode line in the test panel.

Base URL (local): http://localhost:8010
Interactive docs: http://localhost:8010/docs (Swagger), /openapi.json
Every error body is JSON: {"detail": "<message>"}. FastAPI's own validation
errors use {"detail": [{"loc": [...], "msg": "...", "type": "..."}]}.
429 responses carry a Retry-After header (seconds), exposed via CORS.

Troubleshooting
  "[Errno 48] Address already in use"
      A server is already running. Find it with
        lsof -nP -iTCP:8010 -sTCP:LISTEN
      then stop it (Ctrl+C in its terminal, or kill <PID>).
  "Another next dev server is already running"
      Next.js allows one dev server per folder.
  "Could not reach the research API"
      The backend is down, NEXT_PUBLIC_API_URL is wrong, or CORS doesn't allow
      the page's origin.
  "GEMINI_API_KEY is missing" after adding the key
      Restart the backend; it reads .env only when it starts.
  "Accounts are temporarily unavailable" (503)
      Check pg_isready, then run: .venv/bin/alembic upgrade head
  Login seems to work, then you're logged out
      Open http://localhost:3000, not 127.0.0.1. The cookie belongs to
      localhost.
  "Too many failed login attempts" / "Too many sign-up attempts" (429)
      [BRANCH] Per-IP limits; wait for the Retry-After time, or restart the
      backend (the counters are in memory).
  "You've used all 20 AI analyses for today" (429)
      [BRANCH] Resets at midnight UTC; raise AI_DAILY_LIMIT_PER_USER in .env
      for development if needed.
  New CSS or Tailwind classes don't appear in `npm run dev`
      A long-running dev server can serve stale CSS after new component folders
      are added. Restart `npm run dev`; verify with `npm run build`.
  Few "Past Week" results
      PubMed can take a few days to index new papers.

11. KNOWN LIMITATIONS AND OUTSTANDING ISSUES
================================================================================

Security
  Resolved on the branch (Step B; see Section 4.10):
    - AI analysis was public with no limits -> login + atomic daily limits.
    - Registration had no throttling -> 5 attempts per IP per hour.
    - Login throttle was per email only -> also 20 failures per IP per 15 min.
    - NCBI key could appear in INFO-level logs -> loggers quieted + redaction.
    - Raw exception text in PubMed errors -> generic user-facing messages.
  Still open:
    S1. In-memory rate limits (login per email/IP, registration per IP, AI
        burst) suit the current single-process development setup but are NOT
        shared across multiple workers or servers and reset on restart. Use a
        shared store (Redis or PostgreSQL) before scaling out. The DAILY AI
        limits are in PostgreSQL and are shared.
    S2. Registration's 409 still reveals which emails are registered (kept for
        usability; rate limiting makes probing slow).
    S3. Production-unsafe defaults: SESSION_COOKIE_SECURE=false and
        CORS_ALLOW_LOCAL_ORIGINS=true.
    S4. No security headers (CSP, X-Frame-Options, X-Content-Type-Options,
        Referrer-Policy) on the frontend.
    S5. Expired sessions are only deleted when that user logs in again.
    S6. Search is public with no rate limit (owner's decision for Step B);
        NCBI calls are still throttled server-side.
    S7. Users behind one shared IP (e.g. a campus network) share the per-IP
        login/registration allowance.

Functional gaps
  F1. No cross-paper synthesis.
  F2. Scheduled delivery exists only in test form [UNCOMMITTED]: off by
      default, dry_run, or allowlist (approved addresses only). Sending to
      other users is NOT possible: it needs a verified sending domain (DKIM)
      and account email verification, neither of which exists. No scheduled
      email has been sent yet (only Step C's manual test email).
  F2d. One-click unsubscribe can't work locally: it needs an https
      PUBLIC_API_URL and email from a DKIM-verified domain. Locally only the
      body link (http://localhost, this computer only) works.
  F2e. The stored copy of a scheduled email holds its unsubscribe token while
      the delivery is pending/sending: at most its grace period (6 h daily,
      24 h weekly/monthly) while anything ticks, but indefinitely if nothing
      ticks at all (scheduler disabled and no run-once); scrubbed on every
      final status, including expiry. Database backups taken in
      that window, Resend's logs and the recipient's mailbox also hold it. A
      leaked token can only unsubscribe that one subscription.
  F2f. Scheduler heartbeat and per-tick limits are in memory (this process).
      Routine tick summaries log at INFO, which uvicorn's console hides; use
      /health or the status command.
  F2b. Email can only reach the Resend account owner's address until a domain
      the owner controls is verified in Resend (ufl.edu can't be). Test
      emails from resend.dev may land in spam. Resend's free plan: 3,000
      emails/month, 100/day.
  F2c. Each preview or test send runs the AI again (1 unit per topic); there
      is no caching between a preview and the send.
  F3. Successful AI analyses aren't cached; re-analyzing the same paper uses
      another unit of the daily allowance.
  F4. No saved-papers library.
  F5. Personalization is shallow: interests are quick-search chips only and
      don't affect ranking.
  F6. No password reset, email verification, or account deletion in the UI.
  F7. No deployment configuration (Docker, CI, hosting).

Rules for safe changes
  - Secrets:
      - Never print, copy or commit values from backend/.env or
        frontend/.env.local.
      - Refer to variables by name. To check a value, compare it in the shell
        without echoing it.
      - Before committing, stage the files, list them, and scan the staged diff
        for the real key values.
      - Log through `logging`; app/logging_setup.py redacts secrets. Never
        lower the httpx/httpcore loggers below WARNING.
  - PubMed stays the only literature source. All NCBI access goes through
    app/services/pubmed.py (PubMedClient). Don't add a second client.
  - All Gemini access goes through app/services/gemini.py (ReportGenerator).
    Tests must mock it; unit tests must never make paid or live calls.
  - Every new Gemini-calling path must go through AiUsageGuard (reserve before
    the call, refund on failure) so the daily limits stay meaningful.
  - Analysis content must come from PubMed by PMID, never from text sent by the
    browser.
  - Database changes:
      1. Edit app/db_models.py.
      2. Run: .venv/bin/alembic revision --autogenerate -m "..."
      3. Review the generated file (expression indexes such as lower(email)
         need checking; CHECK constraints need IS NOT NULL where a value is
         required, because NULL comparisons pass a CHECK).
      4. Run: .venv/bin/alembic upgrade head
      Keep migrations additive; never delete existing data.
      tests/test_migrations.py fails if the models and migrations drift apart.
  - Database tests empty the tables in healthcare_research_test. Never point
    TEST_DATABASE_URL at a database whose name doesn't end in _test.
  - Don't send repeated failed logins to the running dev backend: your browser
    shares 127.0.0.1, so you would rate-limit yourself (restart clears it).
  - Backend error messages must be safe to show users. Map new failures in
    app/routers/errors.py, and never forward provider messages.
  - The frontend talks to the backend only through src/lib/api/client.ts. Keep
    src/lib/api/types.ts in sync with the backend models.
  - Next.js 16 differs from older versions. Read
    frontend/node_modules/next/dist/docs before using new APIs. A client
    component that uses useSearchParams needs a <Suspense> boundary, or the
    build fails.
  - Test UI changes in `npm run dev` (Strict Mode double-runs effects) AND in a
    production build. Allow for preserved routes: check visibility in browser
    tests. Restart `npm run dev` if new CSS doesn't appear.
  - Ports: backend 8010, frontend 3000. Use spare ports (e.g. 8021-8024 /
    3021-3024) for throwaway test servers, and stop them afterwards.

Where to start on the roadmap
  R0 (review and commit Step D) first. Every new Gemini call must go through
  AiUsageGuard (or the scheduler's GlobalAiBudget), and every email through
  services/email.py with the Step C/D safety checks. Never resend a
  needs_review delivery by hand: use `python -m app.jobs.digests resolve`.
